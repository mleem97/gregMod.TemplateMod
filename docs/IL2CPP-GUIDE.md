# IL2CPP mod development guide

## Use generated proxies

Compile against the assemblies generated by the same MelonLoader version and game build that users run. Regenerate them after game updates.

Do not use managed assemblies copied from a different game version as a permanent workaround. Signature drift can produce runtime crashes even when compilation succeeds.

## Type injection

Managed `MonoBehaviour` classes attached to Unity objects must be registered with `ClassInjector.RegisterTypeInIl2Cpp<T>()` before `AddComponent<T>()`.

Provide the `IntPtr` constructor required by Il2CppInterop and register each type once.

## Harmony

Prefer explicit patch targets. For unstable or private game APIs, resolve targets through `AccessTools` and fail with a clear log message when the target is absent.

Avoid doing heavy work inside prefixes or postfixes. Capture the minimum state and hand longer work to a feature service or the main-thread dispatcher.

## Unity lifecycle

Scene loading and unloading can temporarily invalidate IL2CPP wrappers. Treat cached Unity objects as scene-scoped unless they are attached to a `DontDestroyOnLoad` host.

Check Unity objects for validity before use and rebuild caches after scene changes.

## Threads

Unity APIs generally belong on the Unity main thread. Network, file, or IPC callbacks should enqueue actions through `MainThreadDispatcher`.

## Input and UI

Input System and IMGUI/uGUI interactions vary by game. Isolate input suppression and cursor management behind dedicated services rather than mixing them into feature logic.

## Logging

Log initialization steps, resolved paths, enabled features, and patch failures. Rate-limit errors in per-frame callbacks to avoid creating unusable log files.
